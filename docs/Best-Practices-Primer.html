Introduction

This learning paper covers some best practices I have discovered from authoring skills for my work in the SRE Agent and is essentially distilled from the official Claude Skill authoring best practices that's been adapted for .NET skill development.

If you're about to write your first skill, or you've written one that didn't work the way you expected, this paper will save you from repeating the mistakes I've already made. The principles here are not theoretical — they come from observing what actually happens when an agent loads your skill in production.

1. Be Concise

The context window is a shared resource that must be conserved as best as possible. The addition of your skill in the context window must compete with the rest of the components of the conversation history such as tool call outputs, system prompts and other skill's metadata.

It is imperative to keep the skill as concise as possible: state of the art models such as Claude Sonnet 4.5 have been trained on a large part of dotnet's code, documentation and issues amongst other inputs.

It's a redundant waste of the context window if you decide to include details that the model is trained on for which it'll produce better results than you would do. Only add context the model doesn't already have.

The Token Budget Test

Before you add any paragraph to a skill, run it through this filter:

QuestionsIf "yes", keep itIf "no", cut it
Does the model really need this explanation?✅❌
Can I assume the model knows this?❌✅
Does this paragraph justify its token cost?✅❌

What This Looks Like in Practice

❌ Bad (~150 tokens) — Explains what the model already knows✅ Good (~50 tokens) — Only the specific pattern
"JSON (JavaScript Object Notation) is a lightweight data format. To read a JSON file in C#, you'll need to use a serialization library. Several options exist including Newtonsoft.Json and System.Text.Json. We recommend System.Text.Json because it's built in. First, install it..." 
## Read JSON configuration
Use System.Text.Json:
```csharp
using var stream = File.OpenRead("appsettings.json");
var config = await JsonSerializer
    .DeserializeAsync<AppConfig>(stream);
```

The bad version wastes tokens explaining what JSON is. The model was trained on millions of JSON examples — it does not need you to explain the format. What it might not know is your team's preferred deserialization pattern. That's the only part worth including.

I've found this is the hardest rule for experienced developers to follow, because our instinct is to be thorough. But thoroughness in a skill is actively counterproductive — every unnecessary token pushes useful conversation history out of the context window.

2. Match Specificity to Risk

Not all tasks carry the same risk. Refactoring a utility method is low-stakes — there are many valid approaches and the tests will catch mistakes. But running a database migration or deployment script is high-stakes — there's exactly one correct way and getting it wrong has real consequences.

Your skill should match its level of specificity to the fragility of the task. I think of this as a spectrum of "degrees of freedom" you give the agent:

Freedom LevelWhen to Use.NET Example
High (text instructions)Multiple valid approaches; the right answer depends on context the agent can seeCode review suggestions, refactoring recommendations
Medium (pseudocode/templates)A preferred pattern exists but some variation is acceptableTest scaffolding with xUnit, report generation templates
Low (exact scripts, no deviation)The operation is fragile, error-prone, or destructiveDatabase migrations, deployment scripts, dotnet publish for AOT
The analogy I use: Think of the agent as a robot exploring a path.
  • Narrow bridge with cliffs on both sides — There's only one safe way forward. Provide exact commands with no room for improvisation. (Low freedom)
  • Open field with no hazards — Many routes lead to the destination. Give a general heading and trust the agent to navigate. (High freedom)

In my experience authoring .NET skills, the mistake I see most often is skills that are too prescriptive for open-ended tasks (the agent ignores the instructions because it "knows better") or too loose for fragile tasks (the agent improvises and breaks something). Getting this calibration right is worth the time investment.

How This Applies to Our .NET Skills

SkillFreedomWhy This Level
analyzing-build-errorsLowCS/NU/MSB error codes each have a specific resolution. Guessing wastes time and often introduces new errors.
writing-xunit-testsMediumThe Arrange-Act-Assert pattern and project setup are fixed, but the test logic varies for every class under test.
creating-minimal-apisMediumMapGroup and endpoint organization are the preferred pattern, but the data model and business logic will differ.
profiling-dotnet-appsLow (commands) / High (interpretation)The dotnet-counters and dotnet-trace commands must be exact — a wrong flag produces useless output. But interpreting the results requires context the agent can see (the user's symptoms, the counter values).

3. Structure Your SKILL.md Well

The structure of your skill file determines whether the agent can quickly find the right information or wastes tokens reading irrelevant sections. I've learned that a well-structured skill is worth more than a comprehensive one — the agent doesn't need to read everything, it needs to find the right thing fast.

3.1 YAML Frontmatter — The Discovery Layer

Every SKILL.md begins with YAML frontmatter that controls when the skill gets loaded. This is the single most important part of your skill because if the frontmatter is wrong, the agent will never select it in the first place.

---
name: debugging-memory-leaks
description: Diagnose and fix memory leaks in .NET applications
  using diagnostic tools, heap analysis, and GC root tracing.
  Use when a .NET application shows increasing memory usage
  or OutOfMemoryException.
---
FieldRules
nameMax 64 chars • Lowercase + hyphens only • No reserved words (anthropic, claude)
descriptionMax 1024 chars • Third person • Must include what it does AND when to use it • No XML tags

The description is what the agent reads when deciding which skill to load from potentially 100+ available skills. Think of it as the one sentence a colleague reads before deciding whether to open your document. If it says "Helps with .NET performance", they'll skip it. If it says "Profile .NET application performance using dotnet-counters, dotnet-trace, and dotnet-dump. Use when diagnosing CPU spikes, memory issues, or slow request handling" — now they know exactly when this is relevant.

❌ Vague — never gets selected✅ Specific — triggers on the right prompts
description: Helps with .NET performance description: Profile .NET application performance using dotnet-counters, dotnet-trace, and dotnet-dump. Use when diagnosing CPU spikes, memory issues, or slow request handling.

3.2 Naming Convention

Use gerund form (verb + -ing) for skill names. This convention makes it immediately clear what the skill does when scanning a list:

✅ Good (clear at a glance)❌ Bad (meaningless)
profiling-dotnet-appshelper
writing-xunit-testsutils
debugging-memory-leakstools
migrating-dotnet-versionsdotnet-stuff

3.3 Progressive Disclosure — The 500-Line Rule

Keep SKILL.md under 500 lines. If your skill needs more content, split the additional material into sibling files. The model only loads these when it actually needs them, which means you're not paying the token cost for a comprehensive API reference every time someone asks a simple question.

my-skill/
├── SKILL.md              # Main instructions (loaded when triggered)
├── REFERENCE.md          # Detailed reference (loaded only when needed)
├── EXAMPLES.md           # Usage examples (loaded only when needed)
└── scripts/
    └── validate.csx      # Utility script (executed, never loaded into context)
Critical Rule I Learned the Hard Way: Keep references one level deep from SKILL.md. I initially had SKILL.md → ADVANCED.md → DETAILS.md, and observed the agent only partially reading DETAILS.md (using head -100 instead of reading the full file). Link everything directly from SKILL.md — no chains.

3.4 The Section Template

Every skill I write follows the same section structure. This consistency means the agent learns the pattern and can navigate any skill quickly:

SectionPurpose
## When to UseActivation conditions — what user prompts trigger this skill
## When Not to UseBoundary guard — redirect to other skills when this one doesn't apply
## InputsWhat the agent needs from the user before starting
## WorkflowNumbered steps with explicit checkpoints between them
## ValidationA checklist the agent uses to verify it succeeded
## Common PitfallsKnown traps with specific, tested solutions

4. Build Feedback Loops Into Every Workflow

This is, in my opinion, the single most important pattern in skill authoring. Without feedback loops, I've observed agents make five changes in a row, then discover that three of them broke the build. With feedback loops, each change is validated immediately, and errors are caught before they compound.

4.1 The Core Pattern: Change → Validate → Fix → Repeat

1. Make your code changes
2. Validate immediately: dotnet build --no-restore
3. If build fails → fix compiler errors → rebuild
4. Run tests: dotnet test --no-build
5. If tests fail → fix → rebuild → retest
6. Only proceed when both pass

I include this pattern in every workflow, even if it feels repetitive. The cost of one extra "validate" step in the instructions is negligible compared to the cost of the agent producing a broken result and the user having to restart.

4.2 Give the Agent a Copyable Checklist

For complex workflows, provide a checklist the agent can copy into its response and check off as it progresses. This prevents the agent from skipping steps when it "thinks" it knows what comes next:

Copy this checklist and track your progress:

- [ ] Step 1: Check the .NET SDK version
- [ ] Step 2: Scan all .csproj files for current TFM
- [ ] Step 3: Update TargetFramework in each project
- [ ] Step 4: Run dotnet restore
- [ ] Step 5: Run dotnet build — fix all errors before continuing
- [ ] Step 6: Run dotnet test — fix any test failures
- [ ] Step 7: Verify target framework updated in all projects
Why this works: The checklist creates a visible contract between the skill and the agent. The agent can see what it's done and what remains. Without it, I've observed agents skip validation steps 60–70% of the time because they're "confident" the changes are correct.

5. Content Guidelines

These are the content rules I enforce in every skill review. They seem minor individually but compound into a significantly better agent experience when followed consistently.

5.1 Never Include Time-Sensitive Information

Skills persist far longer than you expect. If you write "use the new API introduced in .NET 9" today, that statement becomes confusing when .NET 11 is current and.NET 9 is the "old" API. Instead, document the current recommended method and put deprecated approaches in a collapsible "Old patterns" section.

❌ Bad — becomes wrong over time✅ Good — always current
"If you're doing this before August 2025, use the old API. After August 2025, use the new API." Document the current method as the default. Put the deprecated approach in an "Old patterns" collapsible section with a note that it's no longer recommended.

5.2 Use Consistent Terminology

Pick one term for each concept and use it everywhere throughout the skill. Inconsistent terminology confuses the agent — it may treat "assembly", "DLL", and "binary" as three different things when you meant the same concept.

✅ Consistent (use throughout)❌ Inconsistent (confuses the agent)
Always "assembly"Mix of "assembly", "DLL", "binary", "module"
Always "project file"Mix of "csproj", ".csproj file", "project config"
Always "extract"Mix of "extract", "pull", "get", "retrieve"

5.3 Always Use Forward Slashes in File Paths

This one bit me early on. Windows-style backslash paths (scripts\helper.py) break on Linux and macOS. Unix-style forward slashes (scripts/helper.py) work on every platform, including Windows. There's no reason to use backslashes — ever.

5.4 Provide Defaults, Not Menus

When the agent encounters "You can use xUnit, NUnit, or MSTest", it often asks the user which one they'd prefer — wasting a turn and breaking the autonomous workflow. Instead, provide a clear default with an escape hatch for the exception case:

❌ Bad — agent asks the user to choose✅ Good — agent proceeds autonomously
"You can use xUnit, or NUnit, or MSTest, or..." "Use xUnit for new test projects.

For existing NUnit projects, follow the NUnit-specific section below."

This pattern — strong default + escape hatch — is something I apply to every choice point in a skill. The agent should almost never need to ask the user to choose between options.

6. Common Patterns That Work Well

Through trial and error, I've found three patterns that consistently produce good agent behavior. I use at least one of these in every skill I write.

6.1 The Template Pattern

When you need the agent to produce output in a specific format, provide a template. Match the strictness to how critical the format is:

  • Strict (for API responses, migration scripts): "ALWAYS use this exact template structure"
  • Flexible (for reports, documentation): "Here is a sensible default format, but adjust sections as needed for the specific context"

6.2 The Examples Pattern

Input/output pairs teach style and tone better than any amount of description. I've found that 2–3 concrete examples communicate the expected behavior far more reliably than a paragraph of prose:

Example 1:
Input: Added null check to user service
Output: fix(UserService): add null-check guard for UserDto parameter

Example 2:
Input: Upgraded target framework
Output: chore(MyApp.csproj): migrate TargetFramework from net8.0 to net9.0

Example 3:
Input: Fixed thread pool starvation in report handler
Output: perf(ReportHandler): convert blocking I/O to async/await

6.3 The Conditional Workflow Pattern

When a skill handles multiple scenarios, guide the agent through the decision point explicitly. Don't make it infer which path to take — spell it out:

1. Determine the scenario:

   Creating a new .NET project?    → Follow "Creation workflow" below
   Migrating an existing project?  → Follow "Migration workflow" below
   Adding a skill to the repo?     → Follow "Skill scaffolding workflow" below

Without this structure, I've seen agents pick the wrong workflow branch about 30% of the time — they'll start migrating when they should be creating, or vice versa. Explicit decision trees eliminate this ambiguity.

7. Evaluation-Driven Development

This is the practice that had the single biggest impact on the quality of my skills: write the test cases before you write the skill. It sounds counterintuitive, but it forces you to define what "good" actually looks like before you start writing instructions.

7.1 The Process

  1. Identify the gap. Run the model on a representative task without any skill loaded. Document exactly where it fails — what it gets wrong, what it skips, what it asks unnecessarily.
  2. Create evaluations. Build at least 3 test scenarios that expose these gaps. For each, write a good.md (ideal behavior) and bad.md (the failure you just observed).
  3. Establish baseline. Score the model's current behavior against your rubric. This is your "before" measurement.
  4. Write minimal instructions. Only enough to address the gaps you identified. Resist the urge to be comprehensive — you're shooting for the minimum effective dose.
  5. Iterate. Run the model with the skill, score it, compare against baseline. If it doesn't improve, the skill has a problem — either it's not concise enough, the description doesn't trigger correctly, or the workflow has a gap.

7.2 The Two-Instance Method

The most effective skill development workflow I've found involves two separate instances of the model:

InstanceRoleWhat You Do
Claude AThe AuthorHelps you design and refine the skill text. Has full context on the best practices, your existing skills, and the specific gap you're addressing.
Claude BThe TesterA fresh instance with no history. Load the skill and give it the real task. Observe what it does — does it follow the workflow? Does it skip steps? Does it ask unnecessary questions?

The cycle is: Ask Claude A to write the skill → Load it in Claude B → Observe Claude B's behavior → Bring the observations back to Claude A → Refine → Repeat until Claude B consistently produces good results.

7.3 What to Watch For During Testing

When observing the agent use your skill, pay close attention to these signals:

What You ObserveWhat It MeansHow to Fix It
Agent reads files in an order you didn't expectYour skill's structure isn't intuitiveReorganize the navigation in SKILL.md
Agent misses important reference filesThe links aren't prominent or explicit enoughMove references higher in the section; make them bold
Agent re-reads the same file multiple timesThat content should probably be in the main SKILL.mdInline the frequently-accessed content
Agent never accesses a bundled fileThe file is either unnecessary or poorly signaledRemove it or improve the reference text that points to it
Agent asks the user to choose between optionsYour skill presents too many alternativesPick a default; move alternatives to escape-hatch sections

These are the mistakes I've either made myself or seen in skill reviews. Every one of them causes observable degradation in agent behavior.

9. Pre-Ship Checklist

I run through this checklist before submitting any skill for review. I recommend printing it out (or copying it into your PR template) until it becomes second nature.

Core Quality

  • Description is specific and includes key trigger terms the user would type
  • Description includes what the skill does AND when to use it
  • SKILL.md body is under 500 lines
  • Additional details are in separate sibling files (if needed)
  • No time-sensitive information anywhere in the skill
  • Consistent terminology throughout (one term per concept)
  • Examples are concrete with real code, not abstract descriptions
  • All file references are one level deep from SKILL.md
  • Progressive disclosure is used — agent doesn't load what it doesn't need
  • Workflows have clear, numbered steps with validation checkpoints

Code and Scripts

  • Scripts handle errors explicitly rather than punting to the agent
  • Error messages are specific and actionable
  • No unexplained "magic numbers" — all values have inline documentation
  • Required packages are listed with exact versions in the instructions
  • No Windows-style backslash paths anywhere (all forward slashes)
  • Critical operations have explicit validation/verification steps
  • Quality-critical tasks include feedback loops (change → validate → fix)

Testing

  • At least 3 test evaluations created (README.md + good.md + bad.md)
  • Tested with multiple models (Haiku needs more guidance; Opus may over-follow)
  • Tested with real usage scenarios, not synthetic examples
  • Team feedback incorporated from at least one reviewer who wasn't the author
  • SkillEvaluator calibration passes (good ≥ 0.85, bad ≤ 0.40)
Final thought: The best skills I've authored are the shortest ones. If you find yourself writing more than 300 lines in SKILL.md, step back and ask: "Am I explaining what the model already knows, or am I adding genuine value?" The answer to that question is the difference between a skill that works and one that's ignored.
